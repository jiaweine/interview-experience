## 一、整体情况

这轮面试以**项目深挖**为主，面试官持续追问 EvoSkill-Harness 项目的业务价值、用户、Skill 设计、线上失败归因与修复、回放验证、离线后训练以及评测指标。后续聊到 OPD、PSD、OPSD 与 GRPO 的比较，手撕了 PyTorch 多头注意力（MHA），最后是开放性的 AI 动态交流。

一个比较明显的特点是：面试官会反复要求**先把项目用外行能听懂的语言讲清楚**，再逐层深入到具体实现；不仅问“用了什么技术”，更关心“为什么这么设计、怎么证明它有效”。

## 二、项目介绍：EvoSkill-Harness

### 1. 项目是做什么的？谁在用？

项目背景：公司内部有很多会议转写、客服聊天等非规范文本，直接用于质检、语料生产或下游模型训练时，容易出现信息混乱、表达不规范、关键实体丢失等问题。

项目目标：让内部团队可以复用一套 Agent 文本处理能力，将原始文本自动加工为可核验、可追溯的结构化或规范化结果，并让系统能利用历史失败案例持续改进处理策略。

主要用户不是普通 C 端用户，而是**内部算法团队、语料生产团队和文本规范化业务团队**。口语转书面语只是其中一项能力，并非整个框架的全部用途。

我的主要工作：**技能图（Skill Graph）生命周期管理**、**Trace Verifier 过程校验**，并参与梳理本体规则、Skill Contract、校验约束等。

### 2. 13 个 Skill 包含什么？

面试官追问“十余类文本能力具体有哪些”，回答大致分成四组：

- **任务和长文本处理**：任务要求解析、长文本切分、多段内容合并；
- **抽取与改写**：候选片段抽取、风格识别、规范化书面改写；
- **校验与核对**：证据对齐、语义一致性、格式和实体校验；
- **执行与纠错**：工具调用规划、失败归因、局部修复。

共 **13 个 Skill**。模型选择下一步 Skill 及其结构化参数，Harness 执行 Skill；只有部分 Skill 会进一步封装真正的外部工具调用。相比固定流水线，技能图可以依据任务组合所需能力，而不是所有任务都机械地执行同一串步骤。

## 三、在线快环：失败归因、局部修复与补丁管理

### 1. 如果有 10 个 bad case，是不是改 10 次 prompt？

不是。先检查每条请求的执行 **Trace**，结合校验结果定位失败原因。要区分系统/工具异常、策略配置问题和模型能力缺口。

如果是可通过策略改进解决的问题，可以调整 prompt、Skill 契约、技能图路由或结构化记忆；如果是模型本身的能力缺口，则进入离线后训练。修复后还要做回归验证，不能只保证那 10 条 bad case 通过。

面试官进一步限定：**只谈在线快环，不谈离线训练**。此时需要澄清两层修复：

- **单次请求内的 Repair**：根据失败节点、已验证的中间结果和必须保留的语义约束，修正出错片段；不直接改写永久配置。
- **跨请求生效的 Skill / Memory Patch**：汇总多条相似 Trace，形成稳定的失败簇，才生成有版本、作用域、可回滚的配置补丁；通过回放验证与灰度后再生效。

### 2. 归因模型和修订模型用什么？

回答使用 **Qwen2.5-7B-Instruct** 作为相关语义推理的基座：

- **FailureAttributor（归因）**：输入执行 Trace、Verifier 的报错证据及当前 Skill 规则，推断失败类型；配合反事实回放验证归因。
- **局部 Repair（修订）**：根据失败原因、相关片段、已通过的中间结果和语义不变量，输出针对性的修复动作。

两者在线调用时都**不修改模型权重**。JSON schema、文本 offset 等确定性校验交给代码实现，复杂语义判断才调用模型。

### 3. 模型不知道业务规则，怎么归因？这些规则怎么制定？

规则不是要求模型事先“记住”所有业务知识，而是拆成结构化配置和自然语言约束，运行时按任务检索相关部分，作为上下文传入。

我参与较多的是：

- **本体规则**：改写时哪些实体、条件、模态不能变，哪些 Skill 组合合法或禁止；
- **Skill Contract**：输入输出字段、前置/后置条件、可接受的结果形式；
- **Verifier 校验规则**：格式、偏移、实体、语义、证据对齐等；
- **bad case 集合**：规则调整后用来测试是否修复问题、是否引入回归。

确定性的校验由程序完成，模糊的语义判断由模型辅助，并结合代码检查结果做交叉验证。

### 4. 怎么限制修订模型，避免把整个 Skill / Prompt 改坏？

单次 Repair 会限定可修改片段，并传入需要保留的语义不变量与已验证中间状态；只允许输出局部修复，不授予它直接持久改写 Skill 配置的权限。

如果生成的是长期生效的 Patch，也不能由模型直接发布。补丁需要满足 Contract / schema 等校验，不允许随意放宽 Verifier 的门禁，并且要经过回归测试、影子运行和灰度。

### 5. 每天几百个 bad case，补丁太多怎么办？会不会冲突或撑爆上下文？

不是每条 bad case 都打一次补丁，而是先**聚类成稳定失败簇**，按类别生成补丁。每个补丁有任务签名、领域、Skill 版本等生效条件，避免全局滥用。

对于有交集的补丁，做 **A、B、A+B 三方回放**，检查叠加效果；冲突时限制适用范围或禁止组合发布。历史经验设置 TTL 或降权淘汰，避免 Memory 无限堆积；反复无法靠配置解决的缺口移交离线慢环。

### 6. 回放怎么证明补丁让系统变好了？

回答了分层回放的思路：

1. 在原始失败簇上重跑，观察专项修复效果；
2. 在历史正常样本和全局回归集上验证，防止“修好一处、弄坏别处”；
3. 对可能冲突的补丁跑 A、B 和 A+B 对比；
4. 检查专项修复率、任务完成率、误接受比例、工具调用成本；
5. 通过后再做真实流量副本的影子验证、小流量灰度；若指标退化则回滚。

核心不是只看 bad case 是否通过，而是证明整体质量没有退化，且成本可接受。

## 四、离线慢环：后训练数据与模型输出

### 1. 后训练数据是什么形式？

离线训练以**决策片段**为基本样本单元，输入包含任务契约、当前状态、可选 Skill / 工具 schema、已验证的工具观测等；目标输出是模型应该采取的动作。

数据来源包括成功轨迹、修复轨迹，以及用于构造对比场景的 hard-negative。错误动作不会直接作为 SFT 的正确标签。训练时对输入 prompt、环境观测、Verifier 反馈等条件部分做 loss mask，主要监督模型生成的路由、调用和修复动作。数据附带原始 Trace 与组件版本等血缘信息。

提到清洗后的 **LoRA-SFT 数据规模约 52 万条**。

### 2. 模型到底输出什么？是工具调用吗？

回答：模型主要输出**结构化动作**，比如下一步选哪个 Skill、传哪些参数、如何局部回退和修复，以及最后的结构化业务结果。底层工具返回的观测属于环境输入，而不是模型需要学习生成的输出。

框架共有 **13 个 Skill**，不是 13 个直接暴露给模型的外部工具。模型输出符合 schema 的 Skill 调用意图，由 Harness 负责真正执行。

### 3. 离线慢环是在训练模型，还是训练 Harness？

主要**训练模型**：LoRA-SFT adapter 和 GRPO 策略权重。Harness 是负责执行、记录 Trace、加工训练数据和评测的工程框架，其代码逻辑不是通过梯度更新训练出来的。

离线侧训练完新模型后，仍需要经过 Harness 的 Regression Gate 验证。线上快环主要修策略与配置，离线慢环负责模型能力和策略本身的参数更新。

## 五、指标和 Verifier 的成功判定

### 1. 任务完成率怎么定义？

**任务完成率 = 满足全部交付约束的任务数量 / 评测任务总数量。**

成功不等于模型“有输出”或链路“不报错”。需要同时满足 Verifier 检查与业务交付条件，涉及格式合规、关键实体保留、语义不变、证据对齐等。

面试中提到同一套离线评测集上，**固定流水线为 86.8%，Agent 框架为 93.5%，提升 6.7 个百分点**。需要注意这里的 93.5% 指任务完成率，而非路由 Top-1 准确率。

### 2. 本来应该选 A，却选了 B 或 C，怎么算对错？

没有唯一的“标准正确路径”。如果选 B 最终也满足全部业务契约，依旧算成功；如果选 C 导致实体丢失、语义漂移等，任务就算失败。

Verifier 不是纯粹依赖一个判别模型：**硬规则代码 + 语义模型**共同完成验收。比如 schema / offset 用程序验证，复杂语义一致性和证据对齐借助 Qwen2.5-7B-Instruct 判别，并综合各项检查。

## 六、后训练方法追问：GRPO、OPD、PSD、OPSD

面试官问有没有做过 **OPD 或 PSD 等蒸馏任务**。我回答项目里没有实际落地这些蒸馏方案，但了解思路，项目采用的是 LoRA-SFT + GRPO。

追问集中在它们与 GRPO 的对比：

- **GRPO**：同一任务采样多条轨迹，用组内相对奖励更新策略；比较容易直接复用现有 Trace Verifier 的轨迹级反馈，不需要准备逐 token 教师软标签。但奖励较稀疏，多步任务的 credit assignment 不够精细。
- **OPD**：在学生实际采样的轨迹上，用教师的概率分布提供更稠密的监督信号；相对依赖教师信号和对应计算开销。
- **PSD / OPSD**：讨论了自蒸馏、教师侧可见额外信息、学生侧不能依赖该特权信息等思路，以及更密集的监督可能带来的收益与泄漏风险。

回答项目选 GRPO 的原因是：Agent 的路由和修复轨迹已有 Verifier 奖励，较容易做轨迹级优化；对 OPSD 所需的高质量特权参考轨迹，项目没有现成且稳定的构造链路。

> 以上是面试中个人对各方案的口头理解与回答，不代表项目实际实现了 OPD / PSD / OPSD。

## 七、手撕代码：PyTorch 实现 MHA

面试官提出共享屏幕，用 PyTorch 手写**多头注意力（Multi-Head Attention）**。题目涉及 Q/K/V 线性投影、分头、缩放点积、mask、softmax、拼接多头和输出投影。

当时记录的实现：

```python
import torch
import torch.nn as nn
import torch.nn.functional as F


class MHA(nn.Module):
    def __init__(self, embed_dim, num_heads):
        super().__init__()
        assert embed_dim % num_heads == 0
        self.embed_dim = embed_dim
        self.num_heads = num_heads
        self.head_dim = embed_dim // num_heads
        self.w_q = nn.Linear(embed_dim, embed_dim)
        self.w_k = nn.Linear(embed_dim, embed_dim)
        self.w_v = nn.Linear(embed_dim, embed_dim)
        self.w_o = nn.Linear(embed_dim, embed_dim)

    def forward(self, q, k, v, mask=None):
        batch_size = q.shape[0]
        q = self.w_q(q).reshape(
            batch_size, -1, self.num_heads, self.head_dim
        ).transpose(1, 2)
        k = self.w_k(k).reshape(
            batch_size, -1, self.num_heads, self.head_dim
        ).transpose(1, 2)
        v = self.w_v(v).reshape(
            batch_size, -1, self.num_heads, self.head_dim
        ).transpose(1, 2)

        attn_score = torch.matmul(q, k.transpose(-1, -2)) / (
            self.head_dim ** 0.5
        )
        if mask is not None:
            attn_score = attn_score.masked_fill(mask == 0, -1e9)
        attn_weight = F.softmax(attn_score, dim=-1)
        out = torch.matmul(attn_weight, v)
        out = out.transpose(1, 2).reshape(
            batch_size, -1, self.embed_dim
        )
        return self.w_o(out)


x = torch.randn(2, 4, 128)
mha = MHA(128, 8)
res = mha(x, x, x)
print(res.shape)  # torch.Size([2, 4, 128])
```

思路：线性映射 Q/K/V → reshape + transpose 拆为多头 → 缩放点积注意力 → 可选 mask → softmax → 注意力权重乘 V → 合并多头 → 输出投影。

自注意力且序列长度为 `n` 时，注意力计算时间约 `O(batch × n² × d)`，显式注意力矩阵的空间约 `O(batch × heads × n²)`（不含 Q/K/V 和其他激活）。实际使用时需要特别注意 mask 是否能广播到 `[batch, heads, q_len, k_len]`，以及全遮蔽行的处理。

## 九、个人复盘

这一轮不仅考技术细节，更看重能否把复杂项目讲成清楚的**业务问题 → 用户 → 技术实现 → 验证指标**：

- **业务表达**：不要一上来就堆 Skill、Trace、LoRA、GRPO 等术语。先说明给谁用、为什么需要、处理前后有什么变化。
- **技术边界**：区分单次 Repair 与持久化 Patch、在线配置迭代与离线模型更新、Skill 与底层 Tool、规则校验与模型语义判断。
- **评测严谨性**：答得清任务成功的定义、无唯一标准路径时怎么判定，以及补丁的回归、冲突检测、成本与灰度。
- **后训练基础**：能讲清训练样本的输入/目标、loss mask、轨迹奖励，以及 GRPO 与蒸馏方案的差异。
- **代码基础**：MHA 属于需要熟练掌握的深度学习手撕题，尤其是张量维度、mask 和复杂度。

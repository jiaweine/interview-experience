## 一、面试整体感受：只问了一个项目，但问得非常细

这次快手可灵平台策略应用算法实习生面试，和很多同时询问几个项目、再穿插算法八股的面试不太一样。**整场主要围绕我介绍的一个 Agent 项目展开，面试官沿着架构设计、数据流转、模块契约、路由算法、评价指标、错误恢复机制一路往下追问。**

从项目为什么这样做，到一段原始文本输入后具体经过哪些 Skill；从 Skill 究竟是代码、Prompt 还是工具，到每个 Skill 的 Schema 如何定义；从 LangGraph State 有什么字段，到路由如何排序、Top1 准确率怎么算，甚至 Verifier 最终返回布尔值还是分数、什么情况局部重试和重新规划，都问到了。

问题本身不算无理取闹，认真考察项目理解当然可以。但连续问到这个程度，**已经接近把整套系统的核心设计、执行链路和评测口径都拆开讲一遍了。**

我基本都跟着问题给出了回答。结果面试后一直没有消息，回头再看这场交流，确实有种把完整项目方案讲出去、却连一个结果都等不到的感觉。

## 二、项目介绍：从固定流水线到技能驱动的动态 Agent

我介绍的是一个面向书面语挖掘、表达规范化等长文本处理任务的 Agent 框架。

原来的固定流水线不区分任务难易，不同请求都跑同一套处理步骤。简单任务会额外执行不必要的模块，复杂任务可能遗漏关键能力，中间出错时也不容易定位，更难对失败步骤进行针对性修复。

为了解决这些问题，我把任务抽象为 Task Signature，把文本处理能力封装成有标准契约的 Skill，并搭建 Graph-of-Skills。系统通过 Test-Time Planning 为具体任务选择执行路径，由 LangGraph 管理执行状态，Agent Harness 作为控制层处理规划、验证和记忆。

执行过程中，通过 Verifier Scoring 检查格式、证据和语义约束，错误优先局部修复，必要时再重规划。Reflexion 负责沉淀执行经验，Memory Retrieval 根据历史任务检索相关经验，辅助之后的路径选择。

**项目评测结果是 Skill 路由 Top1 准确率 92.8%，多步任务完成率相比固定流水线提升 7.6 个百分点。**

这个项目的设计重点是动态组合能力、过程可验证，以及失败后尽量避免整条链路从头重跑。

## 三、先问记忆反哺，再要求拿一个具体例子讲完整执行链路

### 1. Reflexion 和 Memory Retrieval 如何实现记忆反哺？

面试官首先问历史经验如何真正反哺规划。

我解释记忆主要分成写入和检索两个环节。Reflexion 将验证成功或修复成功的任务轨迹抽象成经验，保存 Task Signature、执行路径、失败类型、修复策略等结构化信息，而不是直接保存整段原始文本。

新任务进入时，Memory Retrieval 根据任务签名查找相似历史经验，提供给规划模块作为路径排序的参考。**历史记忆不能替代当前任务的原始证据，更不能突破本次任务的硬约束。** 同时需要对长期记忆做去重、质量过滤，避免失败或过时经验反过来污染决策。

### 2. 从原始文本到最终结果，每一步具体怎么执行？

随后面试官要求我直接给一个输入实例，完整说明当前状态、调用哪些 Skill、为什么调用，以及本人具体负责的模块。

我以一段包含方案讨论、后续再看、没啥问题就先这么做等口语表达的文本为例，讲了整条链路：

1. **Task Package 和 Task Signature。** 输入不仅有原文，还有任务约束与输出 Schema。解析后确定需要片段抽取、风格判断、规范化改写和原文证据，锁定实体、语义极性、条件等不可随意变更的信息。
2. **请求子图和路径规划。** 原文很短，就跳过长文本切分、压缩等不必要的 Skill，激活候选片段抽取、边界修正、分类、规范化、证据选择和验证等能力，再由规划模块选择合适路径。
3. **候选片段抽取与分类。** 找出口语化片段，保留原文字符偏移，判断它们对应的风格和问题类型。
4. **规范化与过程校验。** 假设初次改写把带条件的弱表述变成了绝对肯定，Verifier 会判为语义漂移，不能因为句子更通顺就放行。
5. **局部修复。** 抽取和分类已经通过校验，就保留这些中间结果，只让规范化 Skill 采用更保守的方式重新输出，而不是整条任务重跑。
6. **结果输出与记忆沉淀。** 对照原文证据完成语义和格式验证，整理结构化结果，再把本次错误与有效修复动作写入 Trace，由 Reflexion 提炼可复用经验。

面试官要求的是**从输入到输出逐步交代系统内部发生了什么**，我也确实围绕每个状态和模块的调用理由作了回答，而不是只画一张框架图就结束。

## 四、Skill 到底是什么？连契约和 LangGraph State 字段都追问了

### 1. Skill 是代码、Prompt，还是普通工具？

面试官继续追问 Skill 在系统里以什么形式存在。

我说明 Skill 并不是单独的一句 Prompt，也不是单一的工具函数，而是具有统一 Manifest 契约的可执行能力单元。不同 Skill 可以采用不同实现：

- 长文本切分、格式校验可以是规则代码。
- 候选片段抽取、风格分类可以是规则与模型结合。
- 书面语规范化等生成型任务可以通过约束 Prompt 和模型完成。

**上层规划看到的是统一的输入输出约束、前后置条件和降级策略，而不是必须理解每个 Skill 底层的实现方式。**

### 2. 输入输出 Schema 怎样定义？LangGraph State 有哪些字段？

随后又问到非常具体的 Schema 定义和 AgentState 字段。

我解释了类似 Pydantic 的契约声明方式，输入、输出字段、类型、必填项、前置与后置条件都需要定义。比如规范化 Skill 要求输入具备已对齐原文的 source_span、问题类型、目标风格和语义约束，输出则包含改写文本及相关信息。如果前置条件没有满足，就不允许这个 Skill 进入候选路径。

LangGraph 的 State 则保存 task_package、task_signature、上下文、检索记忆、候选技能、请求子图、候选路径、当前计划、中间结果、校验结果、错误状态、修复历史、资源预算、Trace 及最终输出。

这些 State 配合 checkpoint 支持中断恢复，让局部失败可以复用已经完成且验证通过的状态。

**一个项目能被追问到 Skill Manifest 的字段要求、LangGraph State 具体保存什么，实际上已经进入相当细的实现层了。**

## 五、路由算法和 Top1 指标：怎么筛 Skill、怎么排序、准确率到底怎么算

### 1. 候选 Skill 从哪里来？优先级怎么定？

面试官接下来继续问整个技能路由过程，甚至问到优先级怎样计算。

我的回答是：先根据 Task Signature 与 Skill Manifest 检查任务意图、Schema、前置依赖和业务硬约束，筛出合法的种子技能；再做依赖与验证闭包扩展，生成请求相关子图，过滤不可能执行的路径。不是把全部技能丢给大模型让它自由挑选，也不是直接靠向量相似度决定路由。

可行性过滤后，再根据历史同类任务的 Verifier 通过情况估计路径可靠性。我介绍了**采用分层 Beta 后验的下置信界作为 RouteScore** 的思路，小样本时向上层任务簇回缩，分数相近再考虑预估调用成本和 p95 延迟。历史记忆只能辅助排序，不能突破硬约束。

这部分我不仅解释了路由流程，还回答了评分依据、低样本处理和分数接近时的决策方式。

### 2. Skill 路由 Top1 准确率 92.8%，到底是什么统计口径？

面试官对这个指标进行了连续追问，先问多技能任务是不是也计算 Top1，之后又确认是否只要求第一步选对，后面的结果就不影响准确率。

我解释，**92.8% 统计的是每个技能路由决策点的 Top1 命中率，而不是一条完整路径只看第一步，更不是整条执行链路一次性判对错。**

多技能任务会产生多个决策点，每次需要选择下一 Skill 时都单独计算命中。若有多个功能等价、经过人工认可的技能，也可以纳入可接受集合。

这个路由指标评估的是是否选对下一步 Skill，不能代表 Skill 的生成、执行、校验全都成功。完整链路最终是否完成，还要看端到端多步任务完成率。

**面试官把同一个指标从不同角度追问，我也把统计粒度、等价技能、路由与执行的区别解释清楚了。**

## 六、Verifier 到底返回布尔值还是分数？错误如何恢复？

### 1. Verifier Scoring 的结果是什么结构？

后面面试官又反复确认 Verifier 是返回通过或不通过，还是返回一个数值分数。

我解释了两者并存的设计：

- **硬门控：** 比如 Schema 合法性、原文字符偏移校验、确定性的关键语义冲突，输出 pass / fail。
- **软评分：** 证据支持度、风格匹配度、语义一致性等输出分维度的连续得分。
- **最终决策：** 上层 Harness 结合硬门控、阈值和边界样本复核，确定当前步骤是否通过；不能把多维结果简单加权成一个总分，让高风格分掩盖严重语义错误。

对于需要输出业务 confidence 的场景，先确保所有硬约束通过，再由上层综合软评分，例如采用保守的最小维度得分，而不是说 Verifier 只吐一个总分。

这个问题在对话里前后出现了不止一次，但我对底层校验结果和上层业务判断的区别进行了澄清。

### 2. 哪些错误局部重试，哪些情况重新规划？

最后又问到局部重试和路径重规划的触发条件。

我说明，像格式不合规、证据不足、单个规范化 Skill 发生语义漂移，如果前面节点的中间状态仍然有效，就只重试失败的当前 Skill，保留已验证通过的结果。项目设置局部重试预算，超过次数仍失败，或者发现路径根本无法满足必要输入时，才会触发重规划。

重规划会回到 Planner 选择其他可行路径，并控制总体重规划次数；如果依然无法成功，标记 review_required，不再无限重试。

面试官最后还确认，一个执行阶段是否只能调用一个 Skill。我解释通常一个逻辑步骤对应一个 Skill，LangGraph 按步骤执行并校验；但长文本 Map 阶段可以在多个 Chunk 上并行执行同一类 Skill。**逻辑步骤数和物理并行调用数不是一回事。**

到这里，面试官已经从总体架构问到了失败时保留哪些状态、预算怎么限制、并行调用怎么算步骤。

## 七、为什么我会觉得像在套完整项目？

回头看整场面试，**问的不是几个抽象概念，而是几乎把系统如何搭建、如何运行、如何评分、怎么处理异常、指标如何统计，都问了个遍。**

从输入输出样例，到任务签名、技能图、Manifest、State、路由评分算法、Verifier 的返回结构，再到局部恢复和重新规划，实际上已经覆盖了一个 Agent 框架的关键设计和执行流程。

我理解面试官要判断项目真实性，也理解需要追问候选人是否真的参与实现。只问项目名称、模型名、指标数字当然不够。但**整场只围绕这一个项目反复深挖，连状态字段、路由置信界、每一步的失败处理都要求解释清楚，最终却没有任何后续消息**，确实会让我产生一种不舒服的感觉。

最直接的感受是，像把一个做过的项目从业务背景、架构、数据流到关键算法都讲明白了，交流结束后却再也没有下文。**我甚至怀疑，对方到底是在评估候选人，还是更想听一套完整的技术实现方案。**

必须说明，这只是我经历这场面试后的主观怀疑。详细询问项目并不等于套方案，我没有证据证明面试官或团队有这种目的。但这场面试带来的感受确实如此，也不打算假装自己完全不介意。

## 八、个人复盘：回答得出，不意味着所有设计都已经得到证明

这次面试从技术问答角度，我至少能够围绕问题给出具体解释，而不是只会背一个名词。但回过头看，**能讲出完整架构，不等于所有设计选择都天然成立。**

比如分层 Beta 下置信界的路由评分，需要进一步交代先验怎样设定、如何避免不同任务簇之间的偏差、为什么取 10% 分位、怎样与成本约束联合优化。

再比如 Top1 准确率，也需要有清楚的标注流程和验证集划分，说明等价技能集合如何确认。Verifier 多维软评分也有阈值标定、人工一致性和异常样本复核的问题。

这些完全可以成为合理的深入追问。如果面试官认为我的方案还不成熟，或者岗位更看重另外的技术经验，我可以接受。

**但方案可继续讨论的地方，和招聘方之后一直不提供后续消息，是两件不同的事。**

## 九、总结：一个项目被问到这个深度，最终连消息都没有

这次快手可灵面试的技术追问确实很细。面试官不是没有认真问问题，恰恰相反，**一个 Agent 项目从整体架构到实际执行、从数据结构到路由评估、从验证器到失败回退，基本全都问了。**

我也根据问题给出了对应解释，甚至用具体例子把输入到输出的完整执行链路讲了一遍。最终是否符合岗位标准可以讨论，我不认为面试回答完了就必须通过。

但既然要求候选人投入大量时间，把一个项目拆开来讲这么深，**招聘方至少应该在有结果时给一个明确的后续答复，而不是面试结束以后就没有消息。**

最让我难受的不是一场面试没通过，而是**认真把整个项目的核心设计都解释了一遍，之后却连流程进展都不知道。**

这场经历让我对快手可灵这次招聘流程的印象很差。也希望其他候选人遇到类似的项目深挖时，既能展示自己的技术能力，也能注意技术交流和过度暴露项目内部实现细节之间的边界。

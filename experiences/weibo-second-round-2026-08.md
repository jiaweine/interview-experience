## 二、项目一：EvoSkill-Harness

### 1. 什么是任务签名（Task Signature），实际解决什么问题？

面试官没有停留在概念上，而是反复要求把它说成一个能落地的流程。

任务签名可以理解为**在 Agent 正式执行技能之前，把用户的自然语言任务编译为结构化、可校验的执行契约**。它不只是“模型自由生成一个 JSON”，也不是从预存的若干固定签名中硬选一个。

例子：

- 用户任务：识别口语表达，改写为正式书面语，以 JSON 输出，并提供证据。
- 原始文本：**“这个方案吧，我们后面再看一下，如果没啥问题的话就可以先这么搞。”**
- 显式业务约束：`target_style=formal_written`、`need_evidence=true`、`domain=office_document`、`max_local_repair=2`。
- 必须保持的内容：条件、否定/极性、时间顺序、实体、模态等；不能把“如果没问题可以先执行”擅自改成“立即执行”。

这类任务签名一般可按以下**五组字段**理解：

| 字段类别 | 典型字段 | 作用 | 主要来源 |
| --- | --- | --- | --- |
| **能力需求** | `intent`、`required_capabilities` | 这次需要抽取、识别风格、改写、证据核验、格式检查中的哪些能力 | 任务描述解析 + 模板补齐 |
| **类型契约** | `input_type`、`output_schema`、`required_fields`、`field_source` | 输入和输出的结构、必填字段、字段来源 | API 显式参数、既定 Schema |
| **语义不变量** | `polarity`、`condition`、`entity`、`quantity`、`time`、`modality`、`order` | 哪些意义不允许被改掉 | 显式约束 + 文本风险扫描 + 领域规则 |
| **领域和本体** | `domain`、`ontology_scope`、`allowed_issue_types`、`allowed_rewrite_operations` | 确定允许使用的概念、改写类型与能力组合 | 领域路由、模板/本体查表 |
| **运行策略** | `need_evidence`、`risk_level`、`latency_budget`、`cost_budget`、`retry_budget`、`allow_abstain`、`human_review_policy` | 控制证据、成本、重试、拒答、人工复核 | API 参数优先，策略模板补齐 |

**具体生成流程**（这段是面试官追问最深的部分）：

1. **显式参数归一化**：业务方接口传入的 `target_style`、`need_evidence` 等，映射成固定枚举与类型，不让模型覆盖明确要求。
2. **任务描述解析**：用规则、轻量分类器和必要时的 LLM 解析器，识别需要的能力集合（例如抽取、风格识别、改写、证据核验、格式校验）。
3. **原文风险扫描**：检查条件词、否定词、模态词、数字、实体、时间顺序等，将需要保留的语义约束补齐。
4. **领域模板/本体加载**：通过 `domain` 选出相关的最小本体范围与合法操作。
5. **冲突与契约校验**：例如任务要求“改写”，但显式约束禁止对应操作时，记录 `conflict_list`，不能静默忽略冲突。
6. **产出 TaskSignature**：后续才由 Graph-of-Skills 构造可行子图，再由 Planner 选择路径和执行 Skill。

**优先级**：显式业务字段 > 任务描述解析 > 领域模板默认值。**每次请求都会编译对应签名**；可以根据签名特征或哈希复用历史的路径骨架，但不是从固定签名清单中随便匹配一个。

#### 如果一开始任务签名就编错了怎么办？

编译阶段有字段类型、约束一致性和冲突检查；执行期间如果 Verifier 多次发现 `task_signature_mismatch` 或路径与任务不匹配，可以回退到 `TaskSignatureNode` 重新解析，并以显式业务字段为准覆盖先前的推断值。关键约束不明确时，可以触发拒答/人工复核，不能为了把链路跑通就擅自放宽限制。

### 2. 为什么这里要用 Graph-of-Skills？

不是简单从 13 个技能中选一个，而是多步任务存在**输入输出字段依赖、执行顺序约束和本体兼容关系**。

例如：

`CandidateSpanExtractor → StyleClassifier → WrittenNormalizer → EvidenceVerifier → FormatValidator`

前一个 Skill 产出的 span、风格或 issue type，可能是下一个 Skill 的必需输入。Graph 的节点是带版本的 Skill，边不是随便连接，而要同时检查 Schema 是否可满足、能力依赖和本体兼容；TaskSignature 用于裁剪当前请求的可行子图，再由 Planner 搜索和排序。这样简单任务可以少走步骤，复杂任务不至于漏掉证据和校验链路。

### 3. 一个标准 Skill 的组成

面试官追问“你们一个标准 Skill 里面具体有什么”。回答包括：

- `skill_name` 与 `version`；
- 输入、输出 Schema 与字段来源；
- `preconditions`、`postconditions`；
- `capabilities` 标签；
- `ontology_in` / `ontology_out`；
- `risk_profile`、执行器 `executor`；
- 失败时使用的 `fallback_chain`。

Planner 依靠这些信息判断调用可行性与成本，Verifier 用后置条件定义检查目标，Repair 利用节点和依赖定位回退范围。

### 4. 路由 Top-1 的 92.8% 怎么算？和任务完成率有什么区别？

面试中提到：

- **Planner Top-1 路由一致率：92.8%**。针对存在规范路径/规范等价路径集合的评测样本，看 Planner 排第一的**完整技能路径**是否命中。它只评估“选路”，**不评估路径执行过程中每个 Skill 生成的文本质量**。
- **多步任务执行有效率：90.4%**。需要经过 Schema、字段来源、本体、语义、证据、格式等整体校验，才计为成功。
- **固定流水线 Baseline：84.3%**。口述的对比提升为 **6.1 个百分点**（90.4% − 84.3%）。

面试官继续追问：规范路径是否唯一？如果有多条合法等价路径，不能机械地要求与单一字符串完全一致，应使用合法路径集合等方式判断，并可辅以 Top-k 覆盖评估。

#### 700 万条到底是什么？验证集怎么标？

对话中提到的 **700 万** 是离线整体跑测的数据规模口径，**不等同于纯人工标注的验证集数量**。规则确定的样本可以通过任务模板、Schema、本体约束得到弱标签；复杂边界样本按领域、风险、问题类型分层抽样人工确认。训练/验证/测试需要按照文本来源、模板族、近重复组隔离，防止数据泄漏。

**当场没有给出独立验证集的确切条数**，不应把 700 万写成“人工标注验证集有 700 万条”。上述数字均为这轮口头回答，尚未依据评测记录复核。

### 5. 开放场景题：用这套 Agent 识别微博营销号怎么设计？

面试官提出假设业务：识别低成本批量发帖、疑似营销的账号。我的回答大致是把任务拆成账号资料获取、行为序列抽取、可疑模式检测、账号分类/打分、证据核验：

1. 编译 `domain=social_media` 的 TaskSignature，保留账号 ID、发帖时间、频次等关键字段。
2. 定义 `AccountFetcher`、`BehaviorSpanExtractor`、`SpamPatternClassifier`、`MarketingAccountScorer`、`EvidenceVerifier` 等**假设场景所需的 Skill**（不代表原项目已有这些技能）。
3. 通过 Schema 依赖与本体规则，裁掉与账号识别无关的文风改写链路。
4. Verifier 检查行为证据是否能指向真实帖子/时间窗，输出账号 ID、可疑模式、置信度和证据；低置信度情况转人工复核或 abstain。

这道题考察的是能否把框架迁移到一个新领域，而不是只背原来做文本规范化的技能名。

## 三、项目二：金融投研检索 / 多模态 RAG

### 1. NDCG 是什么？提升 6.7 个百分点怎么理解？

`NDCG` 是 **Normalized Discounted Cumulative Gain**，评价排序结果相关性及靠前程度。面试官接连问缩写、绝对值、百分比与公式。

```text
DCG@k  = Σ(i=1..k) (2^rel_i - 1) / log2(i + 1)
NDCG@k = DCG@k / IDCG@k
```

其中 `rel_i` 是第 `i` 位结果的相关性等级，`IDCG` 是理想排序对应的 DCG。NDCG 常在 0 到 1 之间（存在相关项且 IDCG > 0 时）。

这里**“NDCG@5 提升 6.7 个百分点”**意味着归一化指标增加 **0.067**，不是相对增长 6.7%。例如从 0.700 到 0.767 只是为了说明换算的**举例**，**不是已经核实的项目真实基线值**。面试官追问基线绝对值时，没有提供可核实的原始记录，因此不应自行编造 0.70 或 0.66 为项目实际值。

### 2. BGE-M3 是微调过的还是直接用的开源权重？

回答是**使用开源预训练版 BGE-M3，没有针对金融领域微调其权重**。主要改进来自查询拆解、多模态证据对象、dense/sparse/multi-vector 混合召回、预算分配、精排、证据核验等检索流程。

#### 文档怎么切块、编码？图片表格怎么办？

- **正文**：依据标题树、小节、段落等语义/结构边界分段，保留 section path、页码等来源信息；不是纯固定长度滑窗。
- **表格**：保留表题、行头列头、单位和单元格数值，线性化成可检索的文本，并保留结构化字段。
- **图表与扫描页**：OCR 提取可核验文本，必要时用 VLM 生成 caption；图表区域、坐标和原始位置另行保存。
- **编码方式**：正文、表格线性化文本、OCR 文本和 caption 可以用 BGE-M3 编码为文本向量，结合 sparse/multi-vector 表示；**不是把原始图片像素直接送给 BGE-M3 作为图像 embedding**。
- **证据关联**：不同表示通过同一个 evidence ID 关联，便于去重、定位和回查。

### 3. Light GraphRAG 到底做什么？节点和边是什么？

我解释的是：不是离线建立一个脱离原文的巨大知识图谱，也不是拿图分数与向量相似度直接相加；它主要在**已经召回并精排的候选证据**上搭建临时的证据关系图。

**节点**例如：query slot、主体/公司实体、报告期或时间、财务指标、事件、文档版本、证据对象（正文 span、表格 cell、图表区域）。

**边**例如：`supports`、`contradicts`、`same_entity`、`same_period`、`same_metric`、`version_of`、`derived_from`。边需能回指原始证据来源。

大致流程：

`BGE-M3 多路召回 → 去重/候选池 → Reranker → Light GraphRAG 证据聚合与冲突检查 → Verifier/生成`

Graph 主要帮助识别“同一问题的分散证据能否组合”“是否混入不同公司、年份或版本的事实”，并在证据缺口时指导补检索。**图不作为早期的第四路召回分数直接与 cosine、BM25 相加**。

### 4. 复杂查询拆解准确率 91.8% 如何定义？

面试中讲的是：针对复杂投研问题，有一份标准结构化拆解标注，包含主体、时间、指标、事件、证据类型、模态、是否需要联网等字段；只有关键字段整体正确才按该样本正确计数，而不是把各字段准确率求平均。口述整体准确率为 **91.8%**，没有提供测试集的独立精确条数。

### 5. DPO 与 PPO 的区别

- **DPO**：以 `chosen / rejected` 偏好对为核心训练数据，使用直接偏好优化目标更新模型；通常不需要完整的“奖励模型 + PPO 在线采样”训练链路。
- **PPO**：通过采样、奖励/优势估计及裁剪的策略优化目标进行更新，常见 RLHF 配方还包括奖励模型等组件，训练流程和成本更复杂。

面试回答侧重：当前项目的偏好数据更偏静态成对样本，适合解释 DPO 的使用动机；不要把“DPO 一定不需要任何奖励估计”或“PPO 必须始终有独立奖励模型”讲成无条件定理。

## 四、现场编程：多个有序召回列表合并去重，取 Top K

### 1. 面试官实际给出的要求

来自 BM25、向量召回、RAG 等不同召回来源的**多个文档列表**；每一路内部都已经排好序。要求**合并、去重，并返回最终 Top K 文档**。

我起初理解成每个元素都带有可比较的 `score`，所以按多路有序链表归并的思路，写了一个维护各路当前元素的堆：弹最高分文档，用 `doc['id']` 去重，再压入该路下一条文档。

面试官随即强调：

> “每个列表已经排完序了。”  
> “列表没有一个具体的分数，只有列表，就排好的列表。”  
> “BM25 的分数和向量分数能直接比较吗？”

**问题核心转变了**：每路只有排名、没有跨路可比较的分数时，不能继续用原始 `score` 做全局最大堆。

### 2. 当场理解偏差和正确的澄清点

- **第一版的误区**：假定每条文档都能读取 `score`，且不同召回方式的分数可直接比。实际上 BM25、cosine、内积等尺度并不相同。
- **第二版的误区**：改成只按“列表编号”做堆键，实质上会优先取完编号靠前的列表，并不能自然推导出一个合理的跨源全局 Top K。
- **应该先问清楚**：每路是否有权重或优先级？跨路排名按什么策略融合？同一文档出现在多路时是否累积贡献？如果没有给出统一评分或融合规则，就**不存在唯一可确定的跨路 Top K 排序**。

一种工程上合理的补全假设是 **RRF（Reciprocal Rank Fusion）**：只利用各路排名位置，为每条文档累计分数，然后去重取 Top K。下面是**复盘后更合理的参考实现，不是当场完整写出的代码**。

```python
from collections import defaultdict
from heapq import nlargest


def merge_recall_topk(recall_lists, k, rrf_k=60):
    """每路只给按相关性排好的 doc 列表，doc 必须有 id。"""
    if k <= 0:
        return []

    fused_scores = defaultdict(float)
    doc_by_id = {}

    for docs in recall_lists:
        local_seen = set()
        for rank, doc in enumerate(docs, start=1):
            doc_id = doc["id"]
            if doc_id in local_seen:
                continue
            local_seen.add(doc_id)

            doc_by_id.setdefault(doc_id, doc)
            fused_scores[doc_id] += 1.0 / (rrf_k + rank)

    top_ids = nlargest(k, fused_scores, key=fused_scores.get)
    return [doc_by_id[doc_id] for doc_id in top_ids]


a = [
    [{"id": 3}, {"id": 1}],
    [{"id": 2}, {"id": 1}],
]
print(merge_recall_topk(a, 2))
```

**复杂度**：设所有列表总长度为 `N`，去重后文档数为 `U`，RRF 需要扫描所有候选，计算和字典存储大约 `O(N)`；使用大小为 K 的 Top K 选择，约为 `O(U log K)`；额外空间约 `O(U)`。如果有其他明确的融合策略，也可以采用轮转、路由权重或校准后排序，关键是要先**定义跨路合并规则**。

如果不同来源的分数已被可靠校准到可比较的尺度，才适合使用基于分数的多路堆归并；否则“每路内部有序”本身不足以推出全局唯一排名。

1. **当时刚刚睡醒，状态不好**，脑子有点昏；题目刚给出来时没有认真确认输入数据格式。

4. 以后碰到类似面试题，应该先明确三件事：输入到底有哪些字段、去重依据是什么、跨路排序依据是什么。代码可以先慢几秒，避免在错误假设上一路写下去。
5. 项目问题也说明：任务签名、Graph-of-Skills、检索指标不能只罗列术语，要准备一个真实例子，把字段来源、执行时序、正确性验证和评测口径讲透。
6. 对**验证集条数、NDCG 的绝对基线**等一时说不准的数字，应坦诚说明未核实，不能拿行业经验估算冒充项目事实。

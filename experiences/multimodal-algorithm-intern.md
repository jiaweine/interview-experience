## 一、项目介绍：EvoSkill-Harness 解决什么问题？

我先介绍了 EvoSkill-Harness。这是一个面向内部语料生产和文本规范化的 Agent 后训练框架。

业务原先使用固定流水线处理文本。简单任务也要运行完整步骤，复杂任务可能遗漏必要的检查环节，中间出错时要全链路重跑，历史成功与失败经验也难以复用。

我们的方案是将文本处理能力拆成具有明确输入输出契约的 Skill，通过 Graph-of-Skills 组织能力依赖和可执行路径，并用 Trace Verifier 做过程级校验。执行失败时优先定位问题、局部修复；线上通过 Skill Patch 和 Memory Patch 更新显式策略，离线将验证过的轨迹用于 LoRA-SFT 和 GRPO 后训练。

我主要负责技能图生命周期管理和 Trace Verifier，也参与后训练数据构造和 Reward 口径设计。项目在约 **700 万条业务语料**的评测背景下，**Skill 路由 Top1 达到 93.5%**，多步任务完成率比固定流水线**提升 6.7 个百分点**。

## 二、自进化到底是怎样实现的？

面试官首先围绕自进化机制展开提问，主要想了解系统会更新什么、如何触发更新，以及在线和离线训练之间是什么关系。

我解释，自进化不是让模型不受限制地修改代码，而是分成**线上快环和离线慢环**。

线上每次执行后会保留完整 Trace，由 Verifier 识别失败的位置和类型。若是路由错误、Prompt 不合适、契约或图边配置不合理等策略缺陷，就先通过 Skill 或 Memory Patch 更新显式规则，再经过轨迹回放、Regression Gate 和灰度发布。若多条合法路径反复失败，说明问题可能不仅是策略选择，而是模型本身的能力缺口，这类样本才进入离线训练链路。

离线环节先对已验证的成功轨迹、修复轨迹进行 LoRA-SFT，让基础抽取、技能调用和修复动作更加稳定；再通过 GRPO 优化不同合法路径和修复策略的选择偏好。

无论是线上 Patch 还是新的模型 Checkpoint，都需要经过回归验证，不能在未经审核的情况下直接替换线上版本。

## 三、Graph-of-Skills：它是图、模型、GNN，还是工作流？

这部分是本次面试反复确认的重点。面试官先后问到 Graph-of-Skills 是否是知识图谱、是不是自己实现的、输入输出是什么、有没有基座模型、能否类比 GNN，以及它和 LangGraph 究竟是什么关系。

### 1. 为什么要用图？是否基于 Knowledge Graph？

我解释 Graph-of-Skills 并不是存放实体和事实关系的知识图谱，而是**描述能力依赖与合法执行连接的技能图**。

图中的节点是带有版本、输入输出 Schema、执行约束的 Skill；有向边表示上游输出可以满足下游的输入和前置条件。能否连边不只看 Schema，还需要验证工具权限、本体规则和业务约束。

技能注册时通过 Registry 生成候选边，再经过规则筛选和历史轨迹回放，避免依赖人工一条条手写整张图。

### 2. 这个图是训练出来的吗？输入输出分别是什么？

我进一步澄清，**Graph-of-Skills 本身不是神经网络，不存在直接对整张图做梯度训练的过程。**

输入任务经过解析得到 Task Signature，其中包含任务目标、必要能力、语义约束和工具权限等信息。系统从完整技能图里抽取请求相关子图，剪掉不合法连接，生成多条可行 Skill 执行路径。

图主要负责约束、依赖校验、路径搜索与版本治理。真正可以学习的部分，是后续用于候选路径排序的模块，以及负责技能调用等行为的大模型策略。项目使用 Qwen2.5-7B 作为后训练基座，图结构的更新则通过配置和 Patch 治理完成。

### 3. 是不是 GNN？和 LangGraph 有什么区别？

我说明项目没有使用图神经网络的消息传递，也没有对技能节点做 GNN 式特征聚合。技能图是显式配置和规则约束的结构，图上做的是路径生成、合法性过滤和剪枝。

LangGraph 则承担底层**执行状态编排**，例如节点之间如何流转、失败后如何跳转、checkpoint 和中断恢复。Graph-of-Skills 在上层决定哪些 Skill 可以组合以及优先选择哪条路径，LangGraph 负责按照选定逻辑驱动执行。

整个流程可以概括为：

1. 业务请求解析成 Task Signature。
2. Graph-of-Skills 筛选合法 Skill，生成候选执行路径。
3. Planner 选择路径，Executor 在 LangGraph 的状态流转中执行。
4. Trace Verifier 检查每一步结果，必要时局部修复。
5. 执行轨迹进入线上 Patch 及离线 LoRA-SFT、GRPO 的反馈闭环。

**技能图不是模型，LangGraph 也不等同于完整的 Agent 业务框架。** 面试中我重点解释了这几个层次的职责边界。

## 四、GRPO 和 PPO：基本思想、Critic、Reward 来源

项目架构交流之后，面试官转向强化学习算法。

### 1. GRPO 的核心思想是什么？

我介绍 GRPO 是 Group Relative Policy Optimization，即组相对策略优化。对于同一个 Prompt，策略模型采样多条输出或轨迹，通过 Reward 对这一组结果评分，并依据组内相对表现计算优势，借此更新模型。

相比采用单独 Critic 网络估计价值的 PPO 训练方式，GRPO 使用组内奖励统计构造相对优势，不需要独立训练一个 Critic。它仍需要控制策略更新幅度，常见实现会使用裁剪目标和参考策略约束。

我还说明了它的代价：同一输入需要多次采样，Rollout 开销增加；如果一组样本的奖励非常接近，就难以形成有效的相对学习信号。所以项目先通过 LoRA-SFT 建立基本动作能力，再进入 GRPO 训练。

### 2. 相比 PPO，GRPO 少了什么？PPO 涉及哪些模型？

面试官接着追问模型组成。

我解释，在常见 Actor-Critic 的 PPO 方案中，Actor 负责生成动作，Critic 负责估计价值并辅助计算优势；训练时还需要保存用于重要性采样比率的旧策略信息。在面向语言模型的 RLHF 实现中，通常还可能有参考策略，以及用于提供奖励的 Reward Model。

**其中需要区分 PPO 算法本身与具体 RLHF 训练系统。** PPO 需要奖励信号，但并不强制要求这个信号一定来自独立训练的神经网络 Reward Model。奖励也可以由环境反馈、业务规则或程序化 Verifier 产生。

在我们的项目里，奖励主要来自可验证的任务执行结果和校验器，而不是单独训练一个 Reward Model。

### 3. 强化学习没有 Reward Model，如何获得回报？

针对这个问题，我再次区分了两个概念：**Reward 是训练必需的数值反馈，Reward Model 只是产生这类反馈的一种方式。**

Critic 预测的是价值或累计回报的期望，不是负责创造环境中的原始奖励。我们的 Agent 场景有 Trace Verifier，可以依据执行结果产生程序化反馈，用来支持后续策略优化。

## 五、Memory Patch：它是不是对话记忆？过长怎么办？

面试官后面回到自进化框架，问 Memory Patch 是否属于 Agent 单次对话里的记忆。

我解释，项目里的 Memory Patch 不是简单的聊天上下文，而是**跨任务的结构化经验条目的版本化更新**。我们将经验区分为语义记忆、情景记忆和过程记忆，分别承载规则、验证过的轨迹，以及失败类型对应的修复经验。

多个 Trace 聚类出稳定失败类型后，可以对相应记忆进行新增、修改或降权，但更新需要经过验证和 Regression Gate。单次请求主要读取已发布的经验，不会直接把未经核验的输出写入长期记忆。

随后又问到记忆条目过多、上下文过长时如何处理。我说明系统不会把全部记忆加载进 Prompt，而是根据 Task Signature、领域与失败类型选择少量相关经验，同时结合：

- TTL 与失效条目淘汰。
- 聚类去重，合并相似的失败案例。
- 版本隔离与旧经验降权。
- 检索后按相关性和可信度控制上下文预算。

这些机制主要用于控制记忆膨胀、历史错误经验影响路由，以及长上下文带来的推理成本。

## 六、LoRA：结构、低秩增量与项目参数

最后，面试官又询问了 LoRA 的架构原理。

我解释 LoRA 不改变 Transformer 的整体主干，而是冻结原始权重，在部分线性层引入低秩矩阵 A、B，让训练过程只更新这部分参数。

对应的低秩权重增量可以写为：

```text
ΔW = (α / r) · BA
W = W₀ + ΔW
```

通常先随机初始化其中一个低秩矩阵，另一个初始化为零，使开始训练时的增量为零，避免一开始就改变原始模型输出。训练完成后，如果实现条件允许，可以将低秩更新合并进线性层权重，以减少额外的推理计算。

我还交代了项目中的配置：主要作用于 Attention 和 MLP 的线性层，**rank 为 32、alpha 为 64**。这部分我从结构、训练参数和推理合并的角度进行了回答。

## 二、Memory Patch 与 Reflection Gate 分别做什么？

面试官先问项目中的 Memory Patch 和 Reflection Gate 究竟有什么作用。

我解释，**Memory Patch 是对长期记忆进行维护的能力单元**。在这套项目设计里，它并不直接篡改原始记忆记录，而是调整记忆的元数据，例如重要性、启用状态、关联关系或是否过期。这样既可以管理记忆质量，也可以保留原始记录供回溯和审计。

**Reflection Gate 是控制是否触发反思的门控模块**。不是 Agent 每执行一步都生成反思，而是在出现执行错误、收到明确反馈等情况下，才启动反思与记忆更新。正常任务跳过反思，避免额外的模型调用、Token 开销和时延。

两个模块的分工不同：前者维护已有记忆的状态，后者控制什么时候值得产生新的反思经验。

### 2. 机制加进来以后会不会明显增加耗时？

面试官也关心性能开销。

我回答，在当时的评测环境下，**840 条测试集的总执行时间从基线约 22 分钟增加到约 31 分钟**。主要新增开销来自触发反思时，需要调用模型生成经验并处理记忆更新。

这意味着新机制并非没有代价，不能只讲准确率提升而不提耗时增长。实际使用时需要控制反思触发频率，并可通过缓存相似任务结果减少重复计算。

**面试问到的不是单纯效果好不好，还包括为了这个提升付出了多少推理成本。**

## 四、真实难点：反思触发泛滥、记忆冲突与伪成功样本

### 1. 实际评测中遇到什么问题？

我介绍了两个比较明显的工程问题。

第一个是**反思触发过多**。早期门控阈值不够严格，部分本来正常的任务也触发反思，造成推理时间增加，而且写入大量没有价值的经验，反过来影响后续检索。

第二个是**Memory Patch 的元数据更新冲突**。同一任务可能出现多条反思经验，更新顺序和优先级处理不好，会出现旧的错误经验没有及时降权、相互冲突的记忆同时生效等问题。

我们通过验证集调整门控条件，并增加记忆冲突检查、同任务经验合并与过滤，改善了这两类问题。

### 2. 最难发现的问题：流程成功，反思却是假的

面试官接着要求说一个真正不好解决的难题。

我提到的是**伪成功样本**。Agent 最终给出的结果可能通过评测，但模型在中间生成的反思并不一定与真实执行原因一致。它可能对成功原因做出错误归因，甚至编出与工具记录不符的解释。

如果系统只根据最终任务状态决定是否允许反思进入记忆，而没有单独检验反思内容的真实性，这种错误经验就可能被保存下来。后续相似任务又检索和使用这条记忆，逐渐使路由和执行策略受到错误经验影响。

这类问题比直接报错更难发现，因为表面上任务已经完成，常规结果指标可能也显示正确，必须结合工具返回、执行 Trace 和反思内容检查，才能定位污染来源。

### 3. 如何避免虚假反思继续污染记忆？

对此我提出了几类改进思路：

- **反思事实校验。** 将反思提及的事件、工具返回和实际执行日志对齐，不能从 Trace 中找到支撑的信息，不允许直接写入长期记忆。
- **改进触发与准入条件。** 不只依赖最终任务是否成功，还检查工具调用异常、最终输出是否与工具结果一致，以及反思自身是否通过校验。
- **记忆可信度与衰减。** 新经验先以较低权重入库，需要经过更多独立任务验证，再逐步提升优先级；过时或错误经验降权。
- **训练阶段进一步约束。** 可以尝试整理结果正确但反思错误的样本进行 SFT 纠偏，或者将反思与日志的一致性作为强化学习奖励信号，但这需要额外标注和训练成本。

**这部分的重点不是声称问题已经彻底解决，而是能识别最终结果正确与中间反思正确不是一回事，并且考虑如何在记忆写入前建立校验机制。**

我也说明过这些方案存在工程取舍：增加校验和训练约束通常能降低风险，但会增加时延或维护成本。

## 五、Skill 自进化框架是什么？Harness 与 Agent 有什么区别？

### 1. Generic Skill 自进化框架

面试官接着问到了 Skill 的自进化机制。

我解释，它不只是存储反思经验，还尝试把失败案例和修正经验反馈给 Skill 定义本身。系统根据经验证的反思与失败样本，生成对 Skill 描述、提示、约束和示例的候选更新，再运行 Harness 评测，观察更新后的效果。

这类更新主要影响 Skill 的提示与配置，不代表直接让模型改写生产代码，更不是更新完就立即上线。若小批量测试显示指标退化，就撤销改动并恢复旧版本。

这里要区分两层：**Memory Patch 维护的是经验记忆的元数据和使用状态；Skill 自进化修改的是 Skill 自身的提示、描述和约束配置**，两者不是同一件事。

### 2. Harness 和 Agent 是什么关系？

我把 Agent 解释为面向业务任务的执行主体，负责理解请求、规划、调用 Skill 与生成结果。

Harness 是外层的执行、治理和评测基础设施，负责版本管理、Trace 日志、校验、补丁发布、回归评测和回滚。

可以理解为，**Agent 负责完成业务，Harness 负责让任务执行过程可观察、可验证、可修复、可回退**。二者职责不同，但在系统中协同工作。

## 六、金融文档处理：最后到底交付什么？

后面的提问转向金融类项目，面试官想了解最终输出，以及系统处理的数据边界。

### 1. PDF、公告和研报最后变成什么？

我介绍，文档处理链路把财报、公告、合同等非结构化文档解析为结构化结果，例如章节、正文段落、表格数据、重要数值和风险条款等 JSON 字段，也保留清洗后的文本内容及摘要，方便后续检索、分析和溯源。

### 2. 处理单个 PDF 还是会向外扩散？

我回答，文档解析入口以用户明确上传或指定的文件为边界，可以是 PDF 或网页内容，也支持对给定文件列表批量处理，但不会因为接收一个文件就自动向外爬取无关数据。

金融资料处理需要遵守文件来源和访问权限，不应把文档解析误理解成不受约束的联网爬取。

## 七、FinDeepResearch：检索规划与普通文件问答有什么区别？

### 1. 用户输入一个问题，系统怎么检索？

我介绍了投研检索从用户问题出发的基本流程，包括文档结构化、切分、向量表示、本地召回、关键词过滤、重排和证据来源记录。

随后进一步说明，**检索规划不是只算一次 Query 与文档的相似度**，而是先将复杂问题拆为 Question Tree，明确不同子问题需要哪些事实和指标，也就是对应的证据槽。

本地文档能提供足够证据时，通过 Embedding、BM25 与公司、报告期等元数据过滤组合检索；如果需要最新公告、监管规则等本地缺失信息，再触发联网搜索进行补证。对这类问题，记录中提到本地证据充分度达到 **0.82** 时可直接走本地检索链路，低于要求时考虑进一步搜索。

召回候选再交给 Reranker，判断是否真正支撑子问题，并通过证据图对多个来源进行聚合。证据够了就停止搜索，避免无限调用工具。

### 2. 最终结果长什么样？

我举了一个针对行业研报中盈利预测的查询例子。系统检索出相关测算、核心假设和不同报告中的数值，最后返回带有来源页码的结构化投研摘要，帮助研究人员比较不同报告的观点与预测差异。

### 3. 与直接把文件上传到通用大模型有什么区别？

面试官还拿普通通用大模型的文件问答方式作比较。

我回答，这类投研系统重点在于**金融文档的前置结构化、复杂表格与版式处理、权限隔离、跨文档检索、数值溯源以及稳定的输出格式**，而不仅仅是让大模型读完 PDF 后回答一个问题。

普通通用模型同样可能具有文件解析、检索和引用能力，所以区别不能简单归结成通用模型完全做不到，而是要看是否建立了可控制的数据处理流程、证据核验和机构内部系统集成能力。

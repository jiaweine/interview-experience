## 一、两个项目都问了，技术交流并不浅

这次奇安信面试，我主要介绍了两个项目：一个是面向文本处理与语料生产的 Agent 后训练框架 EvoSkill-Harness，另一个是金融深度投研系统 FinDeepResearch。

面试官不是简单听完项目介绍就结束，而是围绕两个项目的架构、实现、训练方法、选型依据不断追问。从 Skill 图、过程验证、线上修复，一直问到 LoRA、GRPO、DPO、GSPO；第二个项目又问了证据充分度、Embedding、Reranker 和损失函数。

**整个过程中，问到的技术问题我基本都给出了回答，也尽量解释了设计动机和具体实现。** 我不认为每个回答都完美，但至少不是对项目一问三不知。正因为双方聊了这么多细节，后面一直没有消息，才让我觉得格外失望。

## 二、第一个项目：EvoSkill-Harness，几乎从架构问到训练细节

我先介绍了 EvoSkill-Harness。这个项目主要处理客服对话、会议记录、口述转写等原始业务文本，解决口语冗余、指代不清、跨段实体关联，以及固定流水线难复用、失败后必须整链路重跑等问题。

整体思路是将文本处理能力封装成有输入输出契约的 Skill，通过 Graph of Skills 规划执行路径，利用 Trace Verifier 进行过程校验和失败归因。线上快环做局部修复、Skill Patch，离线慢环使用 LoRA-SFT 和 GRPO 优化动作、路由及修复策略。项目评测中，Skill 路由 Top1 为 93.5%，多步任务完成率相比固定流水线提升 6.7 个百分点。我主要负责技能图生命周期管理和 Trace Verifier，也参与后训练数据与评测口径设计。

### 1. 具体有哪些 Skill，技能图的节点和边是什么？

面试官先问系统到底处理什么任务，十多种 Skill 都是什么能力。

我解释了 TaskParser、LongTextChunker、ContextMerger、CandidateSpanExtractor、WrittenNormalizer 等能力的用途，以及 Skill 的输入输出 Schema、证据锚点和语义约束。

接着追问 Graph of Skills 的构成。我说明节点不仅是函数，还绑定版本、Schema、前后置条件、验证器和降级策略；有向边代表上游输出能够满足下游输入要求，但还需要过滤本体、权限和风险约束。候选边由 Schema 兼容性生成，再经过规则与历史轨迹验证，在线上按照 Task Signature 抽取局部子图、硬剪枝、重排序并保留 fallback 路径。

这些问题我都结合实际链路进行了回答，并非只解释一个技能图概念。

### 2. Trace Verifier 怎么评分？Skill Patch 和 Regression Gate 怎么做？

面试官继续问格式、证据、风格、语义四个维度分别如何评分，以及依靠规则还是模型 Judge。

我解释了 JSON Schema、字段类型、原文字符偏移和来源哈希这类确定性规则作为硬门禁；风格和复杂语义再结合模型 Judge、NLI 做辅助判断，重点约束实体、否定、条件、模态等不能随意变化的信息。

后面又问到 Skill Memory Patch、Regression Gate、轨迹回放以及补丁失败后如何处理。

我回答了线上 Patch 修改的对象，以及契约兼容、目标 badcase、全局回归、安全与成本、轨迹回放和影子验证等上线检查。**如果补丁没有通过门禁，不是直接把失败样本全部丢去训练，而是先区分作废、缩小适用范围、维持旧版本，或者已发布时回滚。** 只有反复修复仍无法解决、且合法路径稳定失败的情况，才会归为能力缺口进入离线训练。

这部分面试官问得很细，我也逐项说明了处理逻辑。

### 3. LoRA 为什么不用全量微调？数据怎么配？初始化怎么做？

接下来重点转向后训练。面试官问成功轨迹、修复轨迹、hard negative 的配比，以及为什么选择 LoRA 而不是全量微调。

我介绍了整理后的 SFT 数据规模约 52 万条，成功轨迹、修复轨迹、纠错式 hard-negative 分别占 55%、30%、15%，并说明按完整 Trace 分组切分训练集，避免同一轨迹的不同片段跨集合泄露。

基座采用 Qwen2.5-7B-Instruct，LoRA 主要考虑训练资源、版本迭代、adapter 管理与回滚。我还解释了低秩矩阵 A、B 的更新方式、A 随机初始化与 B 置零的原因，以及 QLoRA 的 NF4 量化、双重量化、分页优化器等区别。

**从选型理由到矩阵初始化都问到了，我也按问题进行了回答。**

### 4. GRPO 是单轮还是多轮？训练框架、奖励和轨迹怎么处理？

关于 GRPO，面试官又连续问了多步 Agent rollout、训练框架、终局 Reward、轨迹长度、长文本切片，之后还延伸到 DPO 和 GSPO。

我解释了 GRPO 训练的是 Agent 的多步执行轨迹：模型产生 Skill 路由或工具调用，环境返回 observation，再继续下一轮，直到完成任务或触发预算上限。训练时对工具返回的 observation 做 mask，只对模型生成的动作 token 计算梯度。

框架上，我介绍了基于 Transformers、TRL GRPOTrainer、PEFT、Accelerate 的改造思路，以及多轮轨迹、组内奖励聚合和工具快照等需要额外处理的部分。

奖励方面，项目采用整条轨迹的终局综合 Reward，不为每一步单独设计 step reward，主要是考虑避免不可靠的过程奖励诱导模型为了局部得分而偏离整体任务目标。

面试官还问了轨迹通常有多少轮、上下文长度怎样控制。我说明常规任务约 3–7 轮，修复会增加轮次，设置最大动作预算；训练上下文上限为 4096，长轨迹按决策点切片，而不是简单砍掉原文或用摘要替代证据。

最后又讨论了 DPO 与 GRPO 的区别，以及 GSPO 与 GRPO 在重要性采样粒度上的不同。

**第一个项目从业务和架构一路问到模型训练机制、框架实现和算法差异，我基本都回答了。**

## 三、第二个项目：FinDeepResearch，主要考察检索与模型选型

第二个项目是我在东北证券研究院实习期间参与的金融深度投研系统，主要面向财报、公告、研报等资料的复杂检索和证据核验。

整体采用问题树拆解、分层检索、重排、证据聚合与验证，解决普通 RAG 容易出现的主体时间错位、财务数据错引、引用不支持结论等问题。项目评测中，复杂任务完成率相比业务基线提升 6.1 个百分点，NDCG@5 提升 7.2 个百分点。我主要负责 Query 拆解、检索规划、证据聚合和校验。

### 1. 如何评价证据充分度？

面试官先问系统怎样判断检索到的证据已经足够。

我从人工标注、模型辅助判断、证据相关性、引用是否能够支持结论，以及子问题的证据覆盖率几个角度说明。核心不是只看检索相似度，还要验证每条结论有没有可靠原文依据。

### 2. 为什么选 Qwen3-Embedding 和 Qwen3-Reranker？

面试官追问 Embedding 与 Reranker 的选型依据，有没有测试过其他模型。

我说明了 Qwen3-Embedding、Qwen3-Reranker 的使用方式，以及与 BGE-M3、GTE、Jina 等方案进行对比的考虑，重点关注长金融文本中的实体、时间和数值匹配，以及 NDCG@5 与延迟的平衡。

这里有一次模型名称和 Embedding 维度的表达不够清楚，面试官又重新确认了所用模型。我随后说明实际检索使用的 Qwen3 系列组合。**这一点我自己也需要复盘：面试时模型版本、维度和选型理由最好一次说准确，避免产生不必要的歧义。**

### 3. Embedding 和 Reranker 用什么损失函数？

面试官继续问对比学习的损失函数、难负样本以及重排模型的训练方式。

我解释了 Embedding 侧使用 InfoNCE，让 Query 与正样本更接近、与负样本拉开距离；金融场景要特别处理主题相近但财务时间或主体不匹配的难负样本。

Reranker 侧，我介绍了 Query 与证据片段的联合建模思路，使用带相关性标签的样本进行训练，并以二元交叉熵优化相关性预测，粗召回后再对候选证据重排。

**第二个项目虽然没有第一个项目问得那么久，但从检索质量评价、模型选型到损失函数，核心问题也都讨论了。**

## 四、最后交流了团队业务方向

面试后半段，面试官介绍了团队工作更偏向网络安全领域，包括预训练、后训练、Agent RL，以及量化、推理压缩和算子优化。

还聊到了希望让模型自主进行漏洞挖掘，这涉及多轮强化学习和长上下文后训练。

我结合之前的 Agent 项目，讨论了多轮工具交互、环境反馈、奖励设计以及安全领域数据处理等可能的技术方向。

从整个交流过程来看，面试官并不是完全不愿意沟通技术需求，甚至介绍了团队实际在做的事情。**这场技术面试本身有一定深度，也确实让我更清楚他们想招什么类型的人。**

## 五、两个项目都问了，面试后却一直没有下文

这次最让我不满意的，不是技术题有多难，而是**面试结束以后，一直没有收到明确的下一步通知或结果。**

两个项目都讲了，技术问题也问了很多。第一个项目从 Skill 图、Verifier、Patch、回归门禁，一直追问到 SFT 数据配比、LoRA 初始化、多轮 GRPO、训练框架、DPO 和 GSPO。第二个项目又围绕金融检索的证据充分度、Embedding、Reranker 和损失函数进行了交流。

我对问到的问题基本都给出了回答，也尽量把设计动机和落地细节讲清楚。**并不是说我答出了问题就必须录用，也不认为没有任何技术短板，但至少这场面试里我确实认真作了准备、认真回答了问题。**

如果面试官觉得我对网络安全业务了解不够，或者我的训练经验、推理优化经验与岗位要求存在差距，这些都可以成为不录用的理由。我完全可以接受招聘的双向选择。

**真正让人失望的是，进行了这样一轮较为充分的技术交流，后续却没有一个清楚的说法。**

作为候选人，我无法知道是在等待流程、岗位发生变化、没有通过，还是单纯没有人再跟进。一直没有消息，只能自己猜。

技术面试可以有很高的要求，也可以有很严格的筛选标准，但招聘沟通不应该在面试结束后就没了下文。候选人的时间和精力同样有成本，准备两个项目、梳理训练细节、回答技术追问，都不是随手就能完成的事情。

## 六、个人复盘：技术面试认真，招聘沟通却令人失望

这次面试确实有值得我自己总结的地方。

一方面，项目如果包含大量模块和训练细节，就应该准备更一致、可核验的说明，尤其是模型名称、维度、训练数据、对比实验和评价指标，不能让表述上的混乱影响可信度。

另一方面，面试官介绍的网络安全 Agent、漏洞挖掘、训练和推理优化方向，也提醒我，虽然已有 Agent 后训练与检索经验，但是否满足特定安全业务和底层推理岗位的要求，还需要结合实际岗位标准判断。

可这些复盘不影响我对招聘体验的评价。

**面试官愿意深入追问，说明技术交流本身并不敷衍；但技术面试认真，不代表面试后的沟通就可以随意缺席。** 一个岗位是否匹配，招聘方当然有自己的判断。只是面试已经结束，候选人不应该一直处于没有结果、也不知道流程走到哪一步的状态。

## 七、总结：可以不录用，但别让候选人的认真投入没有回应

总体来说，**奇安信这次面试的技术考察比较全面，两个项目都问了，问题也基本回答了，但后续一直没有消息，确实令人失望。**

和那种项目都不认真听、问两句就结束的面试不同，这次面试官至少愿意围绕具体技术展开讨论。所以我不想把技术面试本身说得一无是处，更没有证据认为对方是故意戏耍候选人。

但也正因为交流并不浅，后续没有明确答复带来的落差才更明显。

**不合适可以直接拒绝，有更匹配的人选也完全可以选择别人。可既然安排了面试，让候选人认真介绍两个项目、回答一连串技术问题，至少应该在流程有结果时给出一个明确通知，而不是让人一直等不到下文。**

最让人不舒服的，不是没通过，而是认真参加完面试之后，连自己究竟处于什么状态都不知道。就这一次经历而言，我对技术交流的评价不算差，但对招聘后续沟通的评价确实很差。

## 二、项目介绍：EvoSkill-Harness 是做什么的？

我介绍的是一套内部面向语料生产和文本规范化的 Agent 后训练框架。

原有业务使用固定流水线处理客服、会议转写等文本，简单任务也会经过不必要的步骤，复杂任务可能缺少校验，中间一旦失败还要整条链路重跑，而且线上问题很难沉淀为可复用经验。

为了解决这些问题，我们把文本处理能力拆分成可组合、带契约的 Skill，利用 Graph-of-Skills 管理技能依赖和执行路径。线上通过 Trace Verifier 做格式、证据、风格、语义四个维度的过程校验，发现问题时先做局部修复，再使用 Skill Patch 调整策略。离线则收集经验证的执行轨迹，通过 LoRA-SFT 和 GRPO 进行后训练。

我主要负责技能图生命周期管理和 Trace Verifier。项目评测中，多步任务完成率相比固定流水线提升了 **6.7 个百分点**，Skill 路由 Top1 准确率达到 **93.5%**。

这部分我把业务背景、技术架构、个人职责和项目指标都作了说明。

## 三、LoRA：同一个知识点换了几个角度连续追问

项目介绍后，面试官没有立刻讨论 Skill 的设计细节，而是首先围绕 LoRA 展开了连续追问。

### 1. 你怎么理解 LoRA？

我回答 LoRA 是参数高效微调方法，冻结基座模型的原始权重，在 Transformer 的部分线性层上增加两个低秩矩阵 A、B，只训练新增的低秩增量。它学习的是任务所需的权重变化，而不是先对原权重做 SVD 压缩。

我也结合项目解释了 LoRA adapter 便于独立版本管理、灰度与回滚。项目中采用 rank 32、alpha 64。

### 2. 能不能一句话概括 LoRA？它到底附着在什么地方？

面试官接着要求用一句话说清楚，并继续追问到底增加了什么、附着在哪里。

我又明确说明，**LoRA 就是在 Transformer 的线性层上附加一对可训练的低秩矩阵，用少量参数学习原权重的任务增量，同时冻结原始主权重**。推理时可以把训练得到的增量合并回原线性层权重。

这一组问题其实是在从定义、结构到部署形式重复确认同一套核心原理。我并没有只说参数高效四个字，而是把矩阵和线性层的关系解释了出来。

### 3. LoRA 为什么省显存？

我说明了冻结大部分参数后，不需要为这些被冻结的权重维护可训练参数对应的梯度和优化器状态，而低秩矩阵的参数量远少于全量微调，所以训练显存占用更低。

当然，冻结主权重不等于完全不需要反向传播过程中的激活与中间计算，LoRA 也不是训练显存接近零。但面试中问到的核心原因，我已经给出了回答。

### 4. rank 应该怎么理解？

我从低秩矩阵中间维度的角度解释了 rank 对增量更新表达能力和可训练参数量的影响。rank 小，开销低，但可能不足以拟合任务；rank 大，容量更高，也有额外成本，未必持续提升效果。

我还说明项目选取 rank 32 是依据验证效果和资源成本进行权衡，而不是简单认为 rank 越大越好。

**关于 LoRA，这几轮从概念、附着位置、显存节省机制到 rank，面试官反复追问的点我基本都覆盖到了。** 回答可以继续讨论精度、层选择和具体训练开销，但至少不是基础原理没有答出来。

## 四、继续追问项目名称、技能图和验证器

### 1. 为什么叫 EvoSkill-Harness？

面试官问项目英文名称和技能驱动自进化的含义。

我解释了 Evo 对应 Evolution，Skill 是契约化的能力单元，Harness 是承载技能调度、执行、过程验证、Patch 和后训练闭环的框架。

所谓自进化，不是每次失败都直接微调基座模型，而是先在线调整技能策略、修复路径，再将稳定的能力缺口整理为离线训练数据。这也是为什么这个项目以 Skill 为核心组织系统。

### 2. Graph-of-Skills 到底是什么？

我说明 Graph-of-Skills 是技能图，**节点是具有完整输入输出契约和版本信息的 Skill，边是满足依赖与执行约束的有向关系**。

边并不是只检查 Schema 是否能对接，还要考虑能力依赖、工具权限和业务风险。技能注册时自动生成候选边，再经过规则及回归验证过滤。收到任务后，通过 Task Signature 从全局技能图筛出局部子图，完成剪枝和可行路径选择，避免所有任务都跑固定流水线。

这一部分我既回答了节点和边的定义，也讲了技能图如何构建、如何在在线任务里发挥作用。

### 3. Trace Verifier 又是什么意思？

面试官还问到了项目里 Trace 和 Verifier 这两个术语。

我解释 Trace 是记录技能选择、工具调用、中间输出、版本和修复过程的任务执行轨迹；Verifier 是过程校验器，会对这条轨迹做格式、证据、风格、语义四维检查，并定位出问题的具体步骤。

它不是只评价最终结果，而是要为局部修复提供失败定位，同时向后训练提供经过校验的轨迹与反馈信号。

**这些项目术语并不是我只写在简历里却讲不清的概念，面试官逐项问，我也逐项解释了。**

## 五、后续交叉问了三个项目，面试结束却没了消息

**如果不合适，可以明确告知；如果还在流程中，也可以说明状态。一直没有下文，确实会让人觉得自己的时间和投入没有被认真对待。**

## 六、个人复盘：答出来了，也不代表没有改进空间

这次面试我自己也有值得复盘的地方。

比如 LoRA 连续几次被要求重新解释，说明即便知道原理，表达时也应该先用一句最简洁的话说明附着位置、可训练参数和为什么节省资源，再根据追问展开矩阵形式与工程收益。

另外，项目名称与系统术语最好在最初介绍时就说得足够直白。面试官不断问英文名称是什么意思、图是什么、Verifier 是什么，也可能是在确认项目包装和实际内容是否一致。我能解释这些概念，但以后可以更早把术语与具体业务动作对应起来。

**有改进空间是一回事，技术问题基本给出了回答却始终没有后续消息，是另一回事。** 我愿意复盘回答质量，但这并不能抵消对招聘流程沟通的不满。

## 七、总结：不要求必过，只希望面试后有个明确结果

这次德赛西威面试最让我失望的，不是 LoRA 连着问了好几遍，也不是几个项目交叉提问。技术面试追问细一些并没有问题，候选人也应该能够解释自己简历上的内容。

**真正让人不舒服的是，我认真介绍了项目，对 LoRA、Graph-of-Skills、Trace Verifier 等问题基本都给出了回答，后面还围绕三个项目继续交流，最后却没有任何明确的后续消息。**

面试可以失败，岗位也不一定合适，但候选人的准备时间、交流投入和等待成本都是真实的。既然安排了面试，至少应该让人知道最终有没有后续。

**不录用我可以接受；问完这么多问题，最后不了了之，这种招聘体验我确实很难认可。**
